# FCU iOS Club 茶會演講互動連線

台下所有人的手機同時從「請看台上」切換成一通假來電。接了播錄音，掛了就回到看台上。
講完再按一下，全場一起變成一個模擬 App，讓他們自己切「新的／舊的」兩個分頁。
還可以再按一下，全場一起打開同一篇新聞報導 —— 人不會離開這一頁。

跑在 Cloudflare Workers + Durable Objects 上，免費方案就能撐 400 人同時在線。

```
輸入暱稱加入  ──►  請看台上  ──►  [主持人按下 Trigger]  ──►  來電畫面
      ↑              ▲                                    ↙          ↘
  音訊解鎖在這一步     ├──────────────────────────  接聽→播錄音    拒接
                     │
                     ├──►  [主持人按下切到 App]   ──►  模擬 App（新的／舊的）
                     │
                     └──►  [主持人按下切到新聞頁] ──►  新聞報導
```

## 為什麼一定要先輸入暱稱才能進場

那個「加入」按鈕不只是收集名單，**它同時是 iOS 的音訊解鎖手勢**。

iOS Safari 只有在使用者手勢裡播放過的 `<audio>` 元素，之後才能用程式碼觸發播放。
鈴聲是被 WebSocket 訊息觸發的，不是使用者點的，少了進場這一下 tap，
主持人按 Trigger 時全場的鈴聲一定不會響。

1. 兩個 `<audio>` 的 `play()` 必須在同一個手勢事件裡同步發出。
   先 `await` 第一個再呼叫第二個，iOS 會判定已經脫離使用者手勢而擋掉。
2. 進場時設 `navigator.audioSession.type = "playback"`（目前只有 Safari 實作），
   把音訊 session 從 ambient 換成 playback，這樣實體靜音鍵開著也還是會出聲。
3. iOS 上 `<audio>` 標籤在靜音鍵開著時會出聲，但 Web Audio 不會 —— 所以鈴聲和
   錄音都走 `<audio>` 元素，不用 Web Audio 合成。

## 跑起來

```bash
npm install
echo "ADMIN_TOKEN=隨便一組長一點的字串" > .dev.vars
npm run dev
```

- 觀眾：`/`（可加 `?room=xxx` 分場）
- 控制台：`/admin`（Cloudflare 靜態資源會把 `/admin.html` 轉到這裡）

部署：

```bash
npx wrangler secret put ADMIN_TOKEN
npm run deploy
```

## 換成你自己的內容

| 要換什麼 | 怎麼換 |
|---|---|
| 錄音 | 放成 `public/recording.mp3`，會自動取代預設的佔位音 |
| 來電者名稱、頭像 | `public/index.html` 最上面的 `CONFIG` |
| 鈴聲 | 覆蓋 `public/ringtone.mp3` |
| 模擬 App 的兩個分頁 | `public/index.html` 最上面的 `APP_CONFIG` |
| 新聞頁的內文 | `public/index.html` 最上面的 `NEWS_CONFIG`，照片放成 `public/news.jpg` |

頁面用 `<audio>` 的兩個 `<source>`：有 `ringtone.mp3` 就用它，沒有才退回
`ringtone.wav`。用瀏覽器原生的 fallback，不必 JS 探測，也就沒有「探測還沒
回來使用者就按了加入」的競態問題。

`ringtone.wav` 是 `scripts/gen-audio.mjs` 合成的馬林巴音色旋律，當作備援。
改了產生器記得跑 `npm run gen:audio` 重新產生（CI 會驗這兩者一不一致）。

> **素材一定要 commit 進 repo。** CI 是從 git checkout 跑 `wrangler deploy`，
> 沒進 repo 的檔案會在下次自動部署時從線上被移除 —— 而且因為有 fallback，
> 不會報錯，只會安靜地換成另一個聲音。

## 最後那個模擬 App 畫面

電話演完之後，主持人再按一次控制台的「切到 App 畫面」，全場手機會一起變成
一個有 TabView 的 iOS App。分頁列左邊是「舊的」、右邊是「新的」，
左到右就是改版前後；一進去停在「新的」那頁。

重點是讓台下自己切著看，而不是你在台上放兩張截圖比給他們看。
自己按過一次，差在哪比較記得住。

分頁列是照 iOS 26 之後的 Liquid Glass 做的：不貼著螢幕底，而是一顆浮在內容上的
玻璃膠囊，內容從它底下捲過去。選中的那一顆自己又是一片玻璃，疊在膠囊上。

兩頁的文字都在 `public/index.html` 最上面的 `APP_CONFIG`，不用動版面程式：

```js
const APP_CONFIG = {
  appName: "我的 App",
  tabs: {
    new: {
      title: "新的",                     // 分頁列上的字
      nav: "新版",                       // 切到這頁時的大標題
      lead: "改版後長這樣。",
      section: "這一版改了什麼",
      items: [
        { title: "第一個改動", detail: "一句話說明它解決了什麼", badge: "NEW" },
      ],
      foot: "補充說明，可以不要",
    },
    old: { /* 同一組欄位 */ },
  },
};
```

`items` 每一列只有 `title` 一定要填。兩頁的 badge 顏色故意不一樣（新的藍、舊的灰）：
來回切的時候，顏色比文字更快讓人知道現在看的是哪一邊。

想先看版面長怎樣，開 `/?screen=app`，不會連線也不會出聲。`?screen=ring`、
`?screen=call` 也是同樣用法。

想改成一進去先看舊版，把 `selectTab("new")` 和 `showApp()` 裡的 `"new"` 換成 `"old"`。

切到 App 畫面不算一輪來電，不會在 CSV 多長出一欄沒人接的紀錄。

## 新聞頁

控制台的「切到新聞頁」會讓全場手機一起打開同一篇報導。預設放的是
[逢甲週報那篇得獎新聞](https://www.fcu.edu.tw/fcuweekly/news-detail/?id=41487)。

**人不會離開這一頁。** 這件事是硬性的：跳出去開瀏覽器就等於斷線，後面的環節
再也接不回來。所以整頁做成 in-app browser 的樣子 —— 上面一條網址列，
底下是文章本身 —— 看起來是個網頁，實際上還在同一份 HTML 裡。
頁尾的來源網址故意是純文字不是連結，手指戳下去不會把人帶走。

內文為什麼是抄在 `NEWS_CONFIG` 裡，而不是即時去抓：

1. 原站送 `x-frame-options: SAMEORIGIN`，`<iframe>` 直接被瀏覽器擋掉。
2. 就算擋得過，400 支手機在同一秒去抓那個 WordPress 頁面，光它自己的字型、
   追蹤碼和裝飾圖就夠把會場 AP 打死 —— 而這正是整套架構最怕的事。
3. 抄進來就不必賭演講當下對方的站還活著、還沒改版。

照片也一樣收進 repo（`public/news.jpg`，86 KB），跟鈴聲同一個道理：大家進場時
就慢慢載好了，主持人按下去那一刻不用再跟網路借東西。所以別替那張圖加
`loading="lazy"`，那反而會拖到要顯示的時候才抓。

換成你自己的報導，改 `NEWS_CONFIG` 就好：

```js
const NEWS_CONFIG = {
  url: "https://…",          // 顯示在網址列上的來源
  kicker: "逢甲週報・校園新聞",
  title: "標題",
  date: "2024.03.28",
  image: "/news.jpg",        // 省略就不顯示圖
  caption: "圖說",
  paragraphs: ["第一段", "第二段"],
  tags: ["資訊工程學系"],
};
```

想先看版面長怎樣：`/?screen=news`。

切到新聞頁不算一輪來電，不會在 CSV 多長出一欄沒人接的紀錄。

## 事後名單

控制台的「下載名單 CSV」會匯出一人一列、每輪來電各一欄：

| 暱稱 | 加入時間 | 第1輪 | 第2輪 |
|---|---|---|---|
| 小明 | 2026-09-11 19:42:03 | 接聽 | 沒反應 |
| 阿美 | 2026-09-11 19:42:11 | 拒接 | 接聽 |

每個人的身分存在 localStorage 的 device id，所以斷線重連回來還是同一個人，
不會被算成兩個。CSV 有 BOM，Excel 開中文不會亂碼。

控制台顯示兩個數字：**在線**和**已就緒**。接聽／拒接照樣寫進資料庫，
只是不即時推送，省掉「每有一個人回報就送一次全場名單」的開銷。

### 清除資料

控制台的「清除名單資料」會把名單、來電輪次、所有回報全部刪掉，不可復原
（會問你兩次）。活動前清掉測試資料用的。

清除的時候有兩個地方會壞：

- 只刪 `people` 的話，現場還連著的人會變成「在線人數算得到、名單卻查無此人」。
  所以清除後會把他們重新登記回去。
- 正響到一半清掉輪次紀錄，那一輪的回報會被記進一個 CSV 裡沒有對應欄位的 rev，
  變成查不到的孤兒資料。所以清除時一併收回「請看台上」。

## 測試

```bash
npm run dev          # 另一個視窗

npm run test         # 43 個邊界情境 + 9 個時間計算
npm run test:load    # 400 人同時湧入 + 廣播扇出

# 對線上環境跑
HOST=wss://你的.workers.dev ADMIN_TOKEN=xxx npm run test
```

涵蓋的情境包括：遲到進場直接看到來電中、斷線重連接回當前場景、同一裝置重連
不會變成新的人、同一輪重複回報只算第一次、上一輪的回報會被丟掉、重按觸發
不會讓全場再響一遍、錯的 token 連不進來也匯不出 CSV、清除資料後現場的人會
重新登記回去、切到 App 畫面或新聞頁不會多記一輪來電。

### 線上實測（400 條真實連線）

```
DO 身上掛著的 guest 連線數 = 400/400
觸發延遲 ms: min 149 / p50 156 / p95 168 / max 168
在線人數 80 秒不掉：400 → 400 → 400 → 400
```

測試腳本刻意分成兩支：

- `test/ballast.mjs` 負責佔住 400 條連線，一條連上了才連下一條。
  單一 Node 行程一次發 400 個 TLS handshake 會把自己的網路堆疊塞爆，
  這樣量到的 4 秒延遲是測試機的假象，不是伺服器慢。真實情況是 400 支手機
  各做一次 handshake，不會有這個問題。
- `test/measure.mjs` 只用十幾個觀察者量延遲，避免本機事件迴圈變成瓶頸。

## 會場網路很爛怎麼辦

整套架構最重要的設計：**觸發那一刻，每支手機只需要收到 42 bytes。**

```json
{"type":"state","scene":"ringing","rev":7}
```

鈴聲、錄音和新聞頁的照片在大家進場時就下載完了。網路再爛，只要還連著，
這 42 bytes 一定過得去。

真正的風險不是頻寬，是時機。400 人要下載的總量約 240 MB：

| 大家進場的時間 | 等效頻寬 | 結果 |
|---|---|---|
| 分散在 10 分鐘 | 3.2 Mbps | 會場 AP 不痛不癢 |
| 擠在 30 秒內 | 64 Mbps | 會場 AP 直接跪 |

所以「提早 10 分鐘讓大家進場」不是禮貌性建議，是這整件事能不能成的關鍵。

### 已就緒

在線不等於準備好。有人剛連上、錄音還在下載，這時候按下去他接了是一片安靜。

手機要等兩個音檔都 `canplaythrough` 才回報就緒，控制台因此顯示兩個數字：

```
在線 382    已就緒 382     ← 全部載完會轉綠
```

你就知道該按了還是再等 20 秒。

### 預約觸發

按下去不是立刻響，而是廣播「`FIRE_DELAY` 毫秒後響」（預設 3 秒），控制台顯示倒數。
這樣網路慢 1、2 秒的人照樣跟大家同時響，不會拖成一片零星的鈴聲。

每支手機的系統時間都不一樣，所以連上後會做 NTP 式對時：送三次
`{type:"sync"}`，用 RTT 折半估時差，取最快那一次。

對時這段有一個防呆很重要：**手機時鐘本身不準的話，算出來的等待時間會是荒謬的值，
那個人就永遠不會響，而你在現場完全看不出來。** 所以算出來超過伺服器允許的最大延遲
就當作時鐘壞了，寧可立刻響。`test/schedule.mjs` 專門驗這件事 —— 它直接從
`public/index.html` 把 `ringDelay()` 抽出來測，測的是真正會出貨的那份程式碼，
不是另外抄一份。

### 還是會壞的情況

1. 錄音沒下載完就被觸發 → 接了是無聲。看「已就緒」再按。
2. 會場防火牆擋 WebSocket → 沒人連得上。少見但致命，可以的話先去現場測。
3. 網路整個掛掉 → 沒救，只能口頭救場。

另外兩件操作面的事：錄音請壓成 mono 64–96kbps 的 mp3，不要丟大 wav；
叫大家關 Wi-Fi 用行動網路，400 支手機擠一台 AP 比各自走 4G/5G 糟得多。

## 免費額度夠不夠

一場 400 人、兩小時、觸發 3 次的活動大約用掉：

| 項目 | requests |
|---|---|
| 400 條連線（含重連抓 3 倍） | ~2,400 |
| 觸發廣播（送出的訊息不計費） | ~0 |
| 接聽／拒接回報（20:1 折算） | ~60 |
| 就緒回報與對時（20:1 折算） | ~80 |
| 心跳（走 auto-response） | 0 |
| 合計 | ~2,500 / 100,000 每日 |

Duration 約 920 GB-s / 13,000 GB-s。靜態檔案不計次也不計流量。

關鍵在 Durable Objects 的 WebSocket 計費方式：**送出的訊息完全不計費**
（主持人按一下，往 400 支手機廣播是 0 成本），收到的訊息 20:1 折算，
WebSocket protocol ping 和 `setWebSocketAutoResponse()` 的心跳都不計費。

其他家免費 realtime 幾乎都卡在 100–200 條同時連線
（Pusher sandbox 100、Ably 200、Supabase Realtime 200），400 人直接爆。

## CI / CD

push 到 `main` 會自動跑測試並部署。測試用 miniflare 在本機跑，
不需要任何 Cloudflare 憑證，所以 PR 也測得動；只有 main 的 push 才會部署。

要讓自動部署生效，需要在 repo 設兩個 secret：

1. 到 Cloudflare dashboard → My Profile → API Tokens → Create Token，
   選 Edit Cloudflare Workers 範本。
2. 加進 GitHub：

```bash
gh secret set CLOUDFLARE_API_TOKEN      # 貼上剛才產生的 token
gh secret set CLOUDFLARE_ACCOUNT_ID     # wrangler whoami 看得到
```

`ADMIN_TOKEN` 是 Worker 的 secret，用 `wrangler secret put` 設定，
不經過 GitHub Actions。

## 現場注意事項

1. 提早 10 分鐘讓大家進場，把連線尖峰跟觸發時間錯開。
2. 上台前務必**拿一支開著靜音鍵的 iPhone 實測**。這是整套最脆弱的環節，
   模擬測試測不出來。
3. iOS 完全不支援 `navigator.vibrate()`，震動只有 Android 會有 ——
   別把效果押在震動上。
4. 會場網路才是最大風險。斷線重連的退避有加抖動，避免 400 人同時湧回來。
